# Cross-Project QA Playbook

## 목적

이 문서는 "테스트는 통과하지만 실제 사용에서는 계속 이상한 문제가 나오는 프로젝트"에 바로 이식할 수 있는 실사용 QA 운영 플레이북이다.
특정 코드베이스 구조를 전제하지 않고, 어떤 프로젝트든 최소한의 규칙 세트로 붙일 수 있게 정리한다.

DX Pack canonical 위치에 두어, 신규 프로젝트가 DX Pack 설치/최신화만으로도 공용 QA 운영 기준을 함께 받게 하는 것이 목적이다.

## 이 문서 하나로 가져가야 할 핵심

1. QA의 기준은 "코드가 맞는가"보다 "사용자가 끝까지 성공하는가"다.
2. 기능 목록보다 사용자 여정을 먼저 검증한다.
3. 버그는 `재현 절차 + 자동 회귀 테스트 + 문서 계약` 3종 세트로 닫는다.
4. Multi-Agent나 코드 리뷰는 QA를 보조할 뿐, 실사용 검증을 대체하지 않는다.

## 이 문서가 필요한 상황

- 테스트는 PASS인데 실제 실행하면 자꾸 다른 데서 깨진다.
- UI, 포커스, 모달, 저장/로드, 단축키, 해상도, 타이밍 문제 같은 런타임 이슈가 반복된다.
- 기능은 늘어나는데 "무엇을 검증해야 하는지" 팀 안에서 기준이 없다.
- 버그를 고쳐도 비슷한 문제가 다시 나온다.

## 이 문서를 읽는 시점

- 새 프로젝트에 실사용 QA 운영 모델을 이식할 때
- 기존 프로젝트의 QA 체계를 재정비할 때
- 프로젝트별 QA 문서 역할을 다시 나눌 때

주의:

- 이 문서는 상위 운영 원칙 문서다.
- 일상적인 제품 기능 수정마다 항상 읽는 baseline 문서로 쓰지 않는다.
- 프로젝트 내부의 실제 체크 항목은 별도 `USER_JOURNEYS`, `BUG_LOOP_PROTOCOL`, `SMOKE_TEST_CHECKLIST`로 내려가야 한다.

## 핵심 운영 원칙

### 1. 행동 계약을 먼저 적는다

기획 문서를 길게 쓰기보다, 각 기능에 대해 아래를 먼저 고정한다.

- 누가 쓴다
- 어떤 순서로 누른다
- 중간에 어떤 창/상태 전환이 있다
- 최종적으로 무엇이 보여야 성공인가
- 실패하면 어디서 멈추고 어떻게 보여야 하는가

예:

- "캡처 완료 후 영역 선택이 끝나면 원래 편집 다이얼로그로 복귀해야 한다."
- "녹화된 스크롤은 실제 휠이 발생했던 위치에서 다시 재생되어야 한다."
- "저장 후 다시 열어도 캡처된 보조 이미지는 유실되면 안 된다."

### 2. 기능 단위보다 사용자 여정을 먼저 본다

버튼 하나, 함수 하나가 아니라 실제 사용자가 밟는 흐름을 기준으로 QA한다.

최소 여정 세트 예시:

1. 생성: 새 작업 만들기
2. 편집: 핵심 데이터/설정 입력
3. 저장: 저장 후 종료
4. 복귀: 다시 열었을 때 상태 유지 확인
5. 실행: 실제 런타임 성공 확인
6. 복귀/예외: 취소, 닫기, 잘못된 입력, 대상 없음 같은 실패 경로 확인

### 3. 실사용에서 자주 깨지는 축을 따로 본다

아래 항목은 일반 단위 테스트와 분리해서 항상 의식적으로 점검한다.

- 포커스: 다른 창이 활성화된 상태에서도 기대대로 동작하는가
- 모달/복귀: 영역 선택, 파일 선택, 팝업 이후 원래 창으로 복귀하는가
- 저장/로드: 저장 직후와 재시작 후 데이터가 같은가
- 좌표/해상도: 창 크기, 배율, 해상도 변화에 의미가 유지되는가
- 단축키/입력: 로컬 단축키와 글로벌 단축키가 충돌하지 않는가
- 타이밍: wait, poll, animation, 느린 로딩에서 깨지지 않는가

## QA 레이어

### 1. 작업 중 즉시 스모크

기능 하나를 고치면 바로 가장 짧은 실사용 경로를 확인한다.

예:

- 다이얼로그 열기 -> 설정 -> OK
- 저장 -> 다시 열기
- 녹화 시작 -> 정지 -> 재생
- 다른 창 활성화 상태에서 단축키 동작

### 2. 자동 회귀 테스트

실사용 이슈가 한 번이라도 났던 경로는 자동 테스트로 고정한다.

우선순위:

1. 상태 전이
2. 저장/로드
3. dialog return
4. runner/runtime flow
5. hotkey/focus

### 3. 릴리즈 전 사용자 여정 스모크

핵심 사용자 여정 5~10개를 짧게 수동 점검한다.
자동 테스트가 충분해 보여도 이 단계는 생략하지 않는다.

## 버그를 닫는 표준 루프

버그는 아래 5단계로 닫는다.

1. 재현 절차를 3~5줄로 고정
2. 기대 결과와 실제 결과를 한 줄씩 분리
3. 자동 회귀 테스트 추가
4. 행동 계약 문서 1줄 보강
5. 관련 사용자 여정 또는 스모크 절차에 반영

이 5단계 중 하나라도 빠지면 같은 버그가 다시 나올 가능성이 높다.

## Multi-Agent와의 관계

Multi-Agent를 쓴다면 이렇게만 쓴다.

- Planner: 위험 상태 전이와 검증 항목 정의
- Executor: 최소 수정 + 회귀 테스트 추가
- Guardian: 실사용 흐름 기준 누락 검토

중요:

- Multi-Agent는 작업 품질을 높이는 운영 장치다.
- 실사용 QA 그 자체는 아니다.
- "에이전트를 나눴다"는 이유로 사용자 여정 스모크를 생략하면 안 된다.

## 새 프로젝트에 붙일 최소 세트

다른 프로젝트에 바로 적용하려면 최소한 아래 4개만 만들면 된다.

1. 이 플레이북
2. 핵심 사용자 여정 목록 1장
3. 버그 처리 루프 1장
4. 릴리즈 전 스모크 체크리스트 1장

권장 파일명 예시:

- `dx_operating_pack/docs/CROSS_PROJECT_QA_PLAYBOOK.md`
- `docs/dev/USER_JOURNEYS.md`
- `docs/dev/BUG_LOOP_PROTOCOL.md`
- `docs/dev/SMOKE_TEST_CHECKLIST.md`

권장 역할 분리:

- 이 문서: 상위 QA 운영 원칙
- `USER_JOURNEYS`: 실제 점검할 대표 흐름
- `BUG_LOOP_PROTOCOL`: 버그 닫는 절차
- `SMOKE_TEST_CHECKLIST`: 릴리즈 직전 짧은 실행 목록

## 새 프로젝트 도입 순서

1. 최근 실제 버그 3개를 모은다.
2. 공통 원인을 사용자 흐름 기준으로 다시 쓴다.
3. 핵심 사용자 여정 5개를 만든다.
4. 각 여정마다 PASS 기준을 한 줄로 적는다.
5. 버그 발생 시 `재현 -> 회귀 테스트 -> 문서 반영`을 강제한다.
6. 릴리즈 전 수동 스모크를 고정한다.

## 빠른 진단 질문

아래 질문에 `아니오`가 많으면 QA 체계가 약한 상태다.

- 이 기능의 대표 사용자 여정을 한 문장으로 설명할 수 있는가
- 저장 후 다시 열기 테스트가 있는가
- 포커스/모달 복귀를 의식적으로 검증하는가
- 실제로 터진 버그가 자동 테스트로 고정되는가
- 릴리즈 전 수동 스모크 여정이 있는가

## 한 줄 결론

실사용 문제를 줄이려면 "기획을 더 많이 쓰는 것"보다 "행동 계약 + 사용자 여정 + 버그 루프"를 운영 규칙으로 고정하는 것이 먼저다.
